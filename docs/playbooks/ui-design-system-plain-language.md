# The AuditGH Screen — A Plain-Language Briefing

**Date:** 2026-09-11
**Audience:** anyone who needs to understand and fund this. No technical background assumed.
**Companion document:** the detailed version, with every measurement and every file name, is
`ui-design-system-report.md`. Everything here comes from there. Nothing here is rounded up,
softened, or dramatized.
**Named appendix:** `ui-design-system-appendix.md`, which lists every single location by name.
It was generated by a script from the source files, not typed.

---

## Start here: this work has been done

This is not a request for approval to begin. The work described below is finished and sitting
in a branch, waiting to be merged. This briefing exists so that the people who will be asked
to approve the merge — and to fund the follow-on — can see what changed, what it bought, and
what it did not buy.

There is one thing it did not buy, and it is stated plainly at the end rather than buried.

---

## What are we talking about?

AuditGH is the screen our security team looks at. It is where findings from automated scans
arrive, get sorted by how serious they are, get assigned to somebody, and get closed out. If
you have ever seen a dashboard with red, orange and yellow badges next to a list of problems,
you have the idea.

Every piece of software like this has what designers call a **design system**: an agreed set
of colours, spacings, text sizes and shapes, written down in one place, that every screen in
the product draws from. Think of a company brand manual. There is one navy, one grey, one
typeface, and every business card and slide deck uses the same ones. Nobody picks a shade of
navy per business card.

**AuditGH did not have one.** Colour was chosen individually, screen by screen, by whoever
built that screen. We counted the decisions: **1,912 of them.**

That is not a criticism of anyone. It is what happens when a product grows quickly. Each
screen was built to work, each one did work, and nobody stood back to look at all of them
together. This is the standing back.

---

## What is the problem?

Seven things. They are not all the same kind of problem — three of them are the product
literally not doing what the code says, and four of them are the product being harder to read
and harder to trust than it should be.

### 1. The same word meant different colours on different screens

"Low severity" was **green** on three screens and **blue** on two others. Two of the three
greens were not even the same green.

Think of a hospital where the *urgent* tray is red on one ward and yellow on the next. Nobody
misreads it on their own ward. Everyone misreads it the first time they cover someone else's.
That is the cost here: an analyst moving between two screens in the same product is reading
two different colour languages, and the product is silently training them to distrust the
colour.

### 2. Thirty-six colour instructions were being thrown away by the browser

This one is not a matter of taste. Thirty-six places in the code asked for a colour using the
wrong grammar — the equivalent of writing a cheque in a currency the bank does not handle. The
browser cannot read the instruction, so it discards it and moves on silently. No error appears
anywhere.

The visible result: parts of the scheduling calendar — the highlight that marks *today*, the
shading on days outside the current month — **were painting no colour at all**. They had been
broken, quietly, for as long as those lines had been there.

One of the thirty-six referred to a colour that had never been defined anywhere in the
product. It was a name pointing at nothing.

### 3. Five of our source files were never in version control

Version control is the system that keeps the official copy of the code — the shared, backed-up,
reviewable master. If a file is not in it, that file exists only on the laptops that happen to
have it. It is not backed up, no one can review changes to it, and a new engineer setting the
project up gets a copy that does not work.

Five files were in exactly that state. One of them is used by essentially every screen in the
product; another is the code that talks to the server. They had been excluded by accident: a
standard configuration file borrowed from a different programming language contained a rule
meant to skip build leftovers, and the rule happened to match the folder these files live in.

**Anyone downloading this project fresh could not have built it.** This is fixed. The files
are now tracked. Their past history cannot be recovered — it never existed — so the record
starts now.

### 4. One hundred and three controls were invisible to screen readers

A screen reader is the software a blind or low-vision person uses; it speaks the screen aloud.
It can only say what a control is if the control has a name attached in the code.

Buttons that show only a small picture — a magnifying glass, a bin, an arrow — have no name
unless somebody writes one. **Forty-six of ours had none.** A screen reader announced them as,
literally, "button". Fifty-seven typing boxes were in the same state: the label printed next
to them on screen was not connected to the box in a way the reader could follow, so it
announced an unlabelled field.

That is one hundred and three controls a person using a screen reader could not identify.

### 5. Text and outlines that were too faint to see

There is an international standard for how much a colour must stand out from the colour behind
it. It is a ratio. Ordinary text needs to reach 4.5 to 1. The outline of something you interact
with — the edge of a typing box, the ring that shows which control your keyboard is on — needs
to reach 3 to 1.

We measured every colour pair in the product. Five were below the standard. The worst were:

- The **edge of every typing box**, at 1.26 to 1. That is a fifth of what it needs. On a pale
  background the box edge was very nearly invisible.
- The **keyboard focus ring**, at 2.59 to 1. This is the outline that shows a keyboard user
  where they are. Below standard, it stops doing its only job.

We could also only measure a third of the product's colours at all — **34 pairs out of 102** —
because the other 68 colours did not exist as named colours. You cannot test a palette that is
not written down anywhere.

### 6. Seventeen emoji were being used as buttons and icons

✓, ✗, 🔍, ⚠, 📁 and others were used as interface elements. Emoji are not drawn by our
software; they are drawn by whatever computer or phone is displaying the page. So they look
different on a Mac, a Windows PC and an iPhone, they cannot be resized to match the icons
around them, and a screen reader reads them by their official Unicode name. The tick mark is
announced as "white heavy check mark".

### 7. Fifteen layouts that could not fit a phone screen

Thirteen tables and grids had a fixed number of columns with no instruction to reduce that
number on a narrow screen. One of them tried to fit six columns into a phone-width window,
giving each column about the width of two characters. Two dialog boxes were set to a fixed
width wider than a standard phone screen.

## What happens if we don't fix it?

These are different in kind, so the consequences are listed separately rather than merged into
one dramatic total.

**The calendar stays broken and nobody reports it.** A highlight that never appears is not a
bug anyone raises a ticket about — people assume the feature does not exist. It stays broken
until someone rewrites that screen.

**A fresh setup of the project fails.** With five files missing from version control, the next
engineer who joins, or the next machine we build, gets a copy that does not run. The cost is
half a day of somebody's confusion, repeated every time it happens, and a permanent dependency
on the specific laptops that hold the only copies. This is the one where the risk is not
hypothetical: it is a single lost or wiped machine away from being real.

**We stay exposed on accessibility.** Public-sector and enterprise customers increasingly ask
for a formal accessibility statement, and accessibility complaints are a regulated matter in
several of the markets we operate in. A product where one hundred and three controls announce
as "button" does not pass that review. Retrofitting names after a customer asks is more
expensive than adding them now, because by then it is a commitment with a date on it rather
than an engineering choice. It also means our own colleagues who use assistive technology
cannot do this job.

**Colour keeps drifting.** Without an agreed set, every new screen adds new shades. The cost
is not the shades; it is that every future change touches more places. A change that should be
one edit becomes a hunt through hundreds. That is the tax we would keep paying.

**Analysts keep second-guessing the colours.** Nothing breaks. People just stop relying on the
colour and read the text instead, which is slower. The product quietly gets less useful than
it looks.

## Are there benefits beyond this?

Yes, and this is the part that justifies the work even if nobody ever files an accessibility
complaint and the calendar never gets noticed.

**Changing a colour is now one edit instead of hundreds.** All colour now comes from a single
file. Rebranding, adjusting for a customer, or fixing a shade that turns out to be hard to read
is a change in one place that flows everywhere. Before, the same change was 1,912 separate
edits and would never have been done.

**We can now prove the claim rather than assert it.** Three scripts are committed alongside the
code. One measures every colour pair against the standard. One checks thirteen rules about the
interface. One is the tool that performed the conversion, kept so the mapping can be inspected.
They can be wired into the automatic checks that run on every change, which means this cannot
quietly come undone. That is the difference between "we tidied it up" and "it stays tidy".

**Dark mode became a design rather than a guess.** Both light and dark now define all 88
colours explicitly. Before, dark mode was correct on the screens where someone had remembered
to handle it.

**Building the next screen got cheaper.** Four reusable building blocks were added — a page
header, a metric tile, a severity badge, an empty-results panel. New screens assemble from
these instead of being drawn from scratch, which makes them faster to build and consistent by
default rather than by discipline.

**Colour is no longer the only signal.** Each severity level now carries a distinct shape as
well as a distinct colour, so the screen still works when printed in black and white, and for
the roughly one in twelve men with a red-green colour vision deficiency.

**We found the version-control gap because we went looking at the whole product.** That finding
came out of measuring the baseline, not out of looking for it. It is the clearest argument for
periodically standing back: the problem had been there long enough that nobody could say when
it started.

## What is involved in resolving it?

**Nothing needs to be purchased.** No licence, no vendor, no subscription. Every tool used is
already in the repository or already installed.

**The main work is done.** For the record, the size of it: 100 existing files changed, and
twelve files that version control had not seen before. The product compiles, passes its type
checks, and builds successfully.

What remains:

**Now — days, not weeks:**

1. **Review and merge.** A normal code review of the branch. The scripts make this easier than
   it sounds: a reviewer can run two commands and see the before-and-after table themselves
   rather than taking the diff on trust.
2. **Turn the two checks on in the automated pipeline.** Roughly an hour of configuration. This
   is what stops the problem returning.

**Next — one to two weeks of one person's time:**

3. **Open the product in a real browser and look at it**, at phone, tablet, laptop and desktop
   widths. This is the gap described below, and closing it is the single most valuable
   follow-on.
4. **One pass with a screen reader** over the main workflows. Our checks prove every control now
   *has* a name. They cannot prove the name is the *right* name, or that the reading order makes
   sense. A person has to listen to it.

**Later — a decision rather than a task:**

5. **Decide what to do about exported reports.** The PDFs and spreadsheets this product
   generates are standalone documents; they leave the product and carry their own appearance
   with them. They are the one remaining place where a report's look can drift away from the
   product's. Either we generate their appearance from the same single file, or we accept the
   seam and review it whenever the palette changes. Both are defensible. It needs a decision,
   not a project.

## What happened when we did open it in a browser

After all of the above was finished and our checks reported nothing left to find, the product
was opened in a browser. It immediately showed two faults on the main dashboard. Both were
caused by this work. Neither could have been caught by any of the checks we had.

**The first** was in the left-hand navigation. The three menu groups are told apart internally
by a label, and all three had accidentally been given the same one. The software cannot keep
track of three things with the same name, so it warned that the menu might display items twice
or drop them entirely.

**The second** was the radar-style graphic on the dashboard. That graphic is *drawn* rather
than laid out, like a picture painted onto a panel rather than text placed on a page. Drawing
works differently: it cannot look up a colour by name from our new single file. It needs the
colour handed to it already worked out. We had given it names. In four places the graphic
stopped with an error; in nine more it carried on, silently painting the wrong colour, which
is the worse of the two outcomes because nothing reports it.

Both are fixed. The second one is now prevented from recurring by a thirteenth automatic check,
which requires every colour used for drawing to be worked out first. Run against the version
with the fault, it reports 27 problems. Run against the fixed version, none.

**Why this is in the briefing rather than buried.** It is the clearest possible evidence for
the limit described next, and for why the follow-on item we are asking for matters. Twelve
automatic checks, plus two other forms of verification, all reported the product clean. A
person opening it found two real faults in minutes.

## What we are not claiming

**No browser was opened** *during the measurement work*. This is the important limit, and it
shapes everything above. The browser session described in the previous section came afterwards,
found two faults, and did not change how anything else in this briefing was measured.

Every measurement in this briefing and in the companion document was taken by reading the
source code and the colour file — not by running the application and looking at it. That was a
deliberate choice: reading the source can cover all 148 files exhaustively and reproducibly,
where clicking through the application covers whatever a person remembers to click.

But it means a specific thing about the layout findings. Our check can prove there is no
instruction in the code that *causes* a page to be too wide for a phone. **It cannot prove no
page is too wide for a phone.** Those are different statements. The first is what we measured.
The second is what item 3 above would establish.

The same distinction applies elsewhere:

- We can prove every picture-only button now **has** a name. We cannot prove the name is
  accurate, or that pressing Tab moves through the page in a sensible order. A person has to
  check that.
- We can prove the 88 defined colours meet the standard. We cannot prove every screen actually
  uses the colour we think it uses, in the handful of cases where the colour is assembled while
  the page is running rather than written down.
- We can prove that buttons sized by a fixed value are large enough to tap. We do not currently
  check buttons whose size is assembled while the page runs, which is most of them. That check
  needs the same browser run as item 3.

So when the companion document says **"zero findings"**, that means *zero findings the
committed checks can see*. It does not mean *zero defects*. We are claiming the first and not
the second, and the difference is item 3 on the list above.

**No access or permission is missing.** None of the gaps above is blocked by a system we cannot
reach, a privilege we do not hold, or a tool we do not own. Every one of them closes by running
the application locally in a browser, which requires the ability to start the development
server and something for it to talk to — and nothing more than that.

### If you read one paragraph

The screen our security team uses had 1,912 individually chosen colours instead of one agreed
set, 36 colour instructions the browser was silently discarding, 103 controls a blind user
could not identify, 5 source files that were never backed up in version control, and 5 colour
combinations too faint to meet the international readability standard. All of it is now fixed
and, more importantly, now measured by scripts that run on every change so it cannot come back.
Then we opened it in a browser once and found two more faults our own checks could not see —
both now fixed, one now checked for automatically. That is the argument for the one thing left:
open the product at four screen widths and confirm with our eyes what we have so far mostly
confirmed by reading the code.
